# CRM Auth and gift checkout release checklist

Scope of this branch is isolated development. Its migrations were exercised on synthetic data; no production migration, credential rotation, project configuration change or deployment was performed.

## Implemented changes

- CRM signs in with named Supabase Auth accounts. The existing private role registry supplies Owner or Staff access, and inactive accounts lose database access even with an unexpired token. Owner retains management access. Staff reads an allowlisted operational projection with active member records, checkout and service details. Staff can enrol or renew members and create validated checkout rows. Direct staff table access is denied by RLS and finance/management RPCs require Owner. There is no Owner PIN prompt.
- Migration order is `20261121000000_gift_cards.sql`, then `20261121010000_crm_auth_gift_checkout.sql`. The latter preserves existing rows and replaces permissive policies only on `members`, `checkouts`, `service_items`, `sales_people`, and `system_settings`. It replaces the gift RPC implementation to link the same transaction with one protected checkout row and disables direct access to the older private operation.
- Checkout carries the chosen member into Gift Cards by UUID. Redemption or redeemed exchange atomically records the service, gross price, applied gift amount, cash top-up, unused value, member and therapist. An invalid/deleted member or other checkout failure rolls back the gift transaction too. A linked gift transaction cannot be deleted or edited like an ordinary checkout. Refunds and reversals of gift redemptions need a separate ledger-controlled workflow before enabling these operations.
- For service gifts, the issue-time value determines the amount available. When the chosen service is cheaper, checkout shows the precise unused value and requires an explicit customer confirmation. PostgreSQL records the confirmation and unused value with the operation, rejects an absent confirmation and revalidates the full quoted price/balance. No signature or biometric data is collected.
- Gift services are linked by code to an existing CRM service. Owners choose that service when configuring gift prices. Gift pricing remains separate from member pricing. Duration and staff pay for a gift checkout come from that CRM service. CRM services in use by the gift catalog can be deactivated; permanent deletion is prevented.
- Owner cash-receipt totals use ordinary checkout amounts, the cash portion of a gift checkout, and actual gift issuance receipts. Older standalone gift top-ups are counted only when there is no associated checkout row. Approvals, redemptions paid from gift balance, and transfers add no cash receipts. The service margin uses service value less staff pay and is separate from receipts. Existing ordinary checkout amounts retain their historical meaning.
- The clinic tables `clients`, `intake_forms`, and `soap_notes` are outside this CRM migration. Their previously identified permissive access requires a coordinated fix with the shared clinic applications. Do not issue clinical access through the CRM role registry.

## Isolated validation

The new integration suite passed all four test groups. Full-stack acceptance passed on Supabase Auth v2.198.0, PostgREST 16.6, PostgreSQL 18.7 and Chromium. It covered password sign-in, valid and unassigned accounts, staff finance restrictions, role deactivation, keyboard-wedge scan input, mandatory unused-value confirmation, linked member history and the owner receipt report. The Preview build guard accepted an explicitly isolated host and rejected the production hostname. A physical scanner was not connected to this environment.

- `node --test tests/crm-auth-integration.test.mjs` exercises the new migration on a synthetic schema modelled on current production constraints, including required payroll and price columns and the member foreign key. Coverage includes access boundaries, unchanged source records, staff enrolment and renewal, ordinary checkout price validation, atomic gift checkout rollback, deduplicated income and lower-value confirmation plus a legacy exchange through the new gateway.
- `npm run lint`, then build with an explicitly isolated `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, and `VITE_ENABLE_GIFT_CARDS=true`. Do not reuse the repo's tracked default project when running locally.
- Optional full-stack runner `tests/e2e/isolated-auth-barcode.mjs` uses official Supabase Auth and PostgREST release binaries, real PostgreSQL, and a Chromium instance. Install `embedded-postgres` and `playwright-core` into a separate scratch directory. Set `YOHOME_E2E_TOOLS` to that directory. Set `YOHOME_E2E_BINARIES` to a folder containing the executable files `auth`, `postgrest` and the Auth release's `migrations` directory. Set `YOHOME_CHROMIUM` if Chromium is not at `/usr/bin/chromium`. To use the headless-shell alternative, install `@sparticuz/chromium` in the same scratch directory and set `YOHOME_HEADLESS_SHELL=true`. Run `node tests/e2e/isolated-auth-barcode.mjs` from the CRM root. The runner uses localhost ports 55433–55437 and builds temporary accounts, signed tokens, and test data. It must not connect to any cloud project.
- Physical scanner handover test: use a test card whose code has leading zeroes. Scan it on an isolated Preview using the same scanner, computer and keyboard layout that will be used at reception. Confirm the exact code and Enter suffix. Then test a second scan at the replacement-card field, confirm that it does not submit the transaction, click Confirm, and reconcile the old/new balances and receipt totals.

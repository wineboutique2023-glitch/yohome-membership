## 全量文件级差异和决定

- `src/App.jsx`：旧页面没有移除；入口登录、角色数据读取及会员/普通结账 RPC 是批准的权限改造。礼券路由、旧 checkout 同事务集成、带礼券时的记录和报表补充是必要增量。回退初审看到的 Dashboard 重命名、Member Profile 重排、普通收入 PDF 的整体换栏，以及普通结账时间/备注的变化。
- `src/App.css`、`src/GiftCards.jsx`：只追加 `.gift-*` 样式，礼券独立组件。没有修改旧 CSS 规则。视图选择切换时清除旧快照，防止 Staff View 显示残留的 Owner 资料。
- `supabase/migrations`：第一份新增礼券资料与账本；第二份增加 checkout 礼券关联字段、非破坏性约束与已批准的 CRM 授权；第三份以函数替换方式纠正旧业务兼容性。旧宽松的 CRM RLS 策略会被批准的授权策略替换。三份均不删除或重建旧表，也不批量改旧资料。临床三张表的策略和记录不在本次迁移范围。
- `vite.config.js`、`.env.example`：隔离 Preview 防护与占位配置。旧线上构建和正式环境变量没修改。
- `tests/`、`tools/start-local-preview.mjs`、`package.json`、`package-lock.json`：隔离测试和本机启动支持；新增依赖为测试工具，没有新增运行时业务依赖。
- `docs/`：礼券、权限、恢复、Preview、临床独立修复和这份影响审查。没有运行时行为。

## 数据风险与上线门槛

- 使用此前依据生产实际列、约束、外键建立的五张 CRM 表结构；隔离测试以虚构数据覆盖会员、历史 checkout、服务及财务字段。生产只读取结构和聚合计数。核查时生产服务有 12 条、无缺失会员价、无空 deleted 的会员或 checkout、且没有会员类型但缺会员关联的旧 checkout。没有读取或复制真实客户资料。这不是全量生产恢复演练。
- 由于旧站直接匿名查询，先切数据库、后换前端会中断营业。正式切换需要维护窗口协调数据库与已验收的 Auth 前端，旧浏览器标签需要刷新。依赖相同 CRM 表的应用、生产 Email Edge Function 和最多数据量时的 Snapshot 仍要实际核验。
- 旧表的删除与恢复规则不应用于已经入账的礼券交易。切换失败时保留礼券流水和关联交易，暂停发卡、兑卡及受影响写入，使用已验收的 Auth 兼容版本或维护页恢复。旧匿名应用不能直接作为安全回退目标。若需要数据恢复，应从已验证备份在隔离环境恢复并对账，生产写回需单独批准。
- 上线审批必须看到可恢复生产备份、同版本隔离恢复结果、原功能和新增功能完整回归、Preview 人工验收（含店内扫码枪和测试邮箱）及可执行维护回退步骤。不得在这些条件缺失时推送生产分支、修改生产 Supabase 或正式部署。

## 本轮验证记录

- 五组数据库集成测试通过。迁移前后对比隔离库既有会员与 checkout 的原字段值，结果一致。另覆盖正常会员折扣、免费首小时补差及记录备注、原 UTC 时间、工资与利润、续期日期校验、权限与礼券入账。

- 尚待实际设备、托管 Preview、指定邮箱投递、生产备份和隔离恢复演练，以及最终完整人工回归。旧版收据、利润、报表和历史数据的逐项人工业务对账仍属于上线验收。

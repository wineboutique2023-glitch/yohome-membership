## Existing access findings

Database metadata showed all five tables have RLS enabled but an unconditional ALL policy for PUBLIC. The anon and authenticated roles have table SELECT, INSERT, UPDATE and DELETE grants. Policies and grants together permit unauthenticated row reads and writes, including deletes, if the Data API exposes the public schema. The grants also include TRUNCATE, TRIGGER and REFERENCES, which should be removed from application roles. TRUNCATE is a database privilege and is not a standard Data API operation. This assessment used metadata only and establishes capability, not evidence of use.

| Table | Exposure | Target access |
|---|---|---|
| members | Membership records and personal details | Owner manages records, recovery and exports. Staff gets narrow member lookup and the approved enrolment/renewal actions. Staff has no bulk export or permanent deletion. |
| checkouts | Checkout records, payment and financial fields | Owner reviews full details and reconciles. Staff creates approved checkouts through server-validated operations and sees operational fields only. Do not grant unrestricted SELECT when hiding staff pay and margin. |
| clients | Shared clinic client records | Authorised clinic users have role- and assignment-scoped access. Membership staff do not gain clinical access by holding a CRM role. Owner access is explicit, with clinical read scope handled by the clinic's authorised roles. |
| intake_forms | Potential health information and intake records | Authenticated clinic workflow or narrowly scoped, expiring submission token. Clinical reads limited to authorised assigned staff. Owner manages governance and access through approved clinic roles. |
| soap_notes | Potential clinical notes | Assignment-scoped clinical staff access, controlled amendments and audited access. No membership staff grants or unauthenticated read/write. |

No public-schema views or publicly callable SECURITY DEFINER functions were found in the metadata check. Related rows and financial configuration in service_items, sales_people, system_settings, therapists and finance_transactions also warrant review. Inspect Data API exposure, column grants, views, callable functions, Edge Functions and Storage, and preserve available access logs in an approved restricted location. Review historical activity and assess possible exposure with the clinic's incident process. Never exercise live delete, write or client-row read as a permission test.

## Gift Card isolation and decisions

The additive migration creates a private schema and one authenticated RPC. The database role list must be provisioned by an authorised database administrator for actual Auth IDs using the private users table. Gift permissions are checked against the active user on every operation. Staff cannot directly access its tables, including the audit ledger or price catalog. Front-end login uses a separate storage key so it doesn't alter the existing CRM session. Existing records and policies are untouched.

The owner registers unused physical cards and maintains a protected gift service catalog. Staff uses barcode scanner input (keyboard-wedge or manual entry). A service gift snapshots the price, covers its original service, or applies the snapshot to an upgrade. A service gift is a single-use entitlement. If a lower-priced alternative is selected the UI discloses the value that will be released. Dollar and legacy cards retain partial balances. Exchange during legacy checkout or on its own preserves the original expiry on the replacement card. The owner can void an unused service gift with an audited zero-balance adjustment and cannot rewrite the original value. Confirm the single-use/lower-price rule and approved expiry policy before release. A gift sale's amount is recorded at face value; discounted issuance is not included. Cash and Tyro top-ups are recorded after confirmation; no external payment integration is implied.

Gift card checkout history is stored in the protected ledger, accessible from the existing Checkout screen. Gift sales, redeemed value, and supplemental receipts are separate totals. Transfers and approved opening balances contribute no sales receipts. No gift entries are inserted into the legacy checkouts table while that table permits unauthenticated changes. Combined reporting, member-linked gift checkout, cancellations/refunds and secure integration with the old Checkout report are follow-up work on the authenticated existing-CRM paths, before production use if those workflows are needed. A checkout event records gift service, payment method, actor and amounts; it does not calculate therapist pay.

## Tests

`npm ci`, `npm test`, `npm run build`. The automated tests seed synthetic users and services into an isolated Postgres-compatible PGlite instance. A React UI smoke test with a simulated API verified the staff menu, the card lookup and quote, and the legacy exchange confirmation. A second isolated run on PostgreSQL 18.7 used distinct connections to confirm one accepted redemption for two checkouts with the same quote, and one recorded sale for two simultaneous calls with the same operation ID. Browser/POS scanner acceptance, real Supabase JWT integration, verified backup restore and shared-app permission regression remain separate release checks.

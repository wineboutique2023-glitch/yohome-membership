# 三张临床表的生产安全修复计划

范围是 Supabase `yohome-clinic` 的 `clients`、`intake_forms` 和 `soap_notes`。本阶段只做源码和数据库结构核查。此前确认这些表有匿名读写风险，本轮没有更改权限或读取病历内容。

## 已核对的共享应用

| 应用 | 目前有证据的关联 | 切换前必须验证 |
| --- | --- | --- |
| `yohome-clinic-v3` | `src/lib/supabase.js` 指向生产项目，`src/App.jsx` 直接查询并写入三张表，也读取治疗师表 | 客户查询、建立及更新，Intake 新建与查询，SOAP 保存、更新及历史查询，各角色可见范围 |
| `yohome-membership` | 使用同一项目的会员、结账和设置等 CRM 表。已核对的源码没有对三张临床表的直接调用 | 用 Owner 和 Staff 回归会员、结账和礼券。CRM 角色本身不授予临床权限 |
| `yohome-finance-tracker` | 源码使用同一项目的 `finance_transactions`，未发现三张临床表调用 | 用正常应用路径做财务读写冒烟测试，确认未改动 Finance 所需授权 |
| 旧版 `yohome-clinic`、`yohome-invoice-system`、客户签到开票及其他已部署版本 | 旧仓库不能证明当前门店正在使用哪个构建或其环境变量。签到与开票的具体部署仍需确认 | 门店列出实际常用链接。核对每个部署的 Supabase ref、服务端函数及真实调用路径。说清是否连接到同一生产项目 |
| `yohome-os-staging` | 已识别为独立 Supabase 项目 | 单独核对是否有跨项目桥接。临床生产修复不更改此项目 |

生产结构显示 Intake 和 SOAP 按外键关联至 clients，三张表的 created_by 都可关联 auth.users。既有记录可能缺少作者或分配信息。迁移时保留原记录，缺少资料的访问分配由诊所授权人员确认。

## 安全切换顺序

1. **确认依赖和现状。** 在 Vercel 点击各门店项目的 **Settings → Git** 和 **Settings → Environments**，查看对应仓库、版本和项目 ref。在 Supabase 点击 **Logs → API / Postgres**，由获授权管理员在只读范围按路径和调用角色汇总近期流量。低流量路径需门店按实际操作验证。记录公开客户 Intake、治疗师保存、自动发票、导出和调用服务身份等入口，只留必要的脱敏证据。
2. **在隔离项目建立新的授权路径。** 治疗师按诊所与实际分配读取客户及病历。客户公开 Intake 使用经审批的短时、限目的提交入口，禁止通过公开接口读取历史。收银和会员 Staff 不取得 SOAP 权限。后台任务只获得其服务需要的最小字段和操作权限。授权与病历方案经批准后，再编写临床专用增量 Migration。
3. **用模拟病历跑一条完整业务链。** 新建客户 → Intake → 治疗师读取授权资料 → SOAP 保存及更正 → 实际使用的签到与发票流程。测试无登录、无分配和已停用账号均被拒绝。验证历史记录、异常回滚，以及所涉应用中已有 SOAP/Intake 功能。做生产备份和隔离还原验收后再申请上线。
4. **协调生产切换。** 批准后安排低峰短维护窗口，冻结临床写入。先发布并验证新版应用的受保护路径，再按受控范围撤销三张表的匿名授权与宽松策略。旧版浏览器标签需要刷新；临床端身份或写入失败时中止后续步骤。恢复营业时核对实际 Staff 和治疗师流程、API 拒绝率及关键日志。
5. **保留恢复路径。** 发生失败，暂停受影响入口并切回已验证的受保护版本或维护页，保留所有写入及审计。生产备份只在隔离环境还原作分析。未做数据对账和单独批准前，不将还原写回生产，也不恢复公开表权限。

待确认事项集中为一项：门店实际使用的临床、客户 Intake 与自动开票链接。仅凭仓库文件无法确定仍在使用的旧部署。
